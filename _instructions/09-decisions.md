# Прийняті рішення

## Архітектурні

### Чому Blazor Server а не WebAssembly
Прямий доступ до БД і сервісів без HTTP API шару. Простіша авторизація через стандартний ASP.NET Core middleware.

### Чому SQLite
Навчальний проект, не потребує окремого DB сервера. При переході на production — замінити на PostgreSQL одним рядком у `Program.cs`.

### Чому LabStatus — int а не enum в БД
EF Core зберігає enum як int за замовчуванням. Конвертація: `(LabStatus)sub.Status` і `(int)LabStatus.Review`.

### Чому ExecuteUpdateAsync для збереження профілю
`AppDbContext` scoped до SignalR circuit. `EnsureLinkedAsync` (в AuthService) і `Profile.razor` використовують один і той самий `DbContext`. Якщо AuthService завантажив сутність, вона відстежується його контекстом — `SaveChangesAsync` з іншого місця не зберігатиме зміни. `ExecuteUpdateAsync` — прямий SQL UPDATE, обходить change tracker повністю.

### Чому GitHub API для комітів у UI, а не git clone
- git clone блокує сервер на десятки секунд для великих репо
- Вимагає встановленого git
- GitHub API повертає коміти з SHA, батьками, авторами миттєво
- `GetBranchCommitInfosAsync` повертає `CommitInfo` з повними SHA і parents[] — достатньо для git-графу

### Чому кастомний dropdown замість нативного `<select>`
Нативний dropdown на Windows ігнорує CSS `background-color` на рівні OS. `color-scheme: dark` не дає повного контролю. Кастомний div-dropdown: повний контроль стилів, hover через CSS класи, скрол через `overflow-y: auto`.

## Grading

### Чому Gemini, а не запуск build/тестів на сервері
Оцінюємо студентські роботи різних доменів (клініка, готель, ресторан) з довільними
назвами класів/методів — жорсткі I/O-тести тут крихкі. Gemini перевіряє **вимоги**
з `checks.json` по коду й повертає структурований done/issues. Раніше планувалась
схема з GitHub Actions + I/O checks.json — від неї відмовились.

### Чому одна перевірка за раз (черга)
git clone + Gemini на кожну задачу — важко й повільно; 100 студентів одночасно
поклали б сервер і вибили квоту. `GradingQueueService` серіалізує перевірки,
`GeminiQuotaService` тримає денний ліміт. Ліміт спроб і дедлайн перевіряються
**повторно** після очікування в черзі.

### Чому один batch-запит до Gemini на всі завдання
Дешевше за квотою й швидше, ніж N окремих викликів; менше шансів упертись у 429.

### Чому системний збій не витрачає спробу
API впав / повернув не той формат — це не вина студента. `GradeAllWithGeminiAsync`
кидає виняток, спроба не списується; списує лише реальний результат або
підтверджений плагіат/підміна репо.

### Чому студент здає коміт а не "поточний стан гілки"
Захист від "я щось зламав після здачі". Студент явно вибирає що здає. CommitMappingJson зберігає маппінг sha→taskNumber.

### Чому score = done/(done+issues), а не число від Gemini
Прозорість: оцінка виводиться з переліку виконаних/невиконаних вимог, а не з
довільного числа моделі. Далі `Scoring.Weighted` зважує задачі за складністю (⭐).

### Anti-plagiarism
Два незалежні гейти ще до Gemini (квота не витрачається): `FindSharedRepoAsync`
(інший студент із тим самим репо → hard-fail) і `FindExactMatchAsync` (повний збіг
рядків з уже перевіреною роботою). Викладач може дозволити повторну здачу
(`PlagiarismApproved`, одноразово) — на випадок, коли чужий URL скопіювали в законного власника.

## Автентифікація

### Чому ASP.NET Core Identity замість Keycloak
Спочатку був Keycloak 24 у Docker: окремий контейнер, admin-паролі в конфігу, кастомні FTL-теми, скидання sub при `down -v`. Для навчального застосунку це зайва інфраструктура. Identity зберігає акаунти в тій самій SQLite базі — застосунок запускається одним `dotnet run`, а Google OAuth підключається опційно ключами в appsettings.json.

### Чому логін/реєстрація — form POST на minimal API, а не інтерактивний Blazor
Інтерактивний circuit (SignalR) не може встановити auth cookie — response вже відправлений. Тому Login.razor/Register.razor рендерять звичайні `<form method="post">` на `/account/login` та `/account/register`, помилки повертаються назад через query string.

### Чому оновлюємо UserId замість створення нового UserLink
Якщо запис студента вже має UserLink (наприклад, після пересоздання акаунта з тим самим email) — нова спроба зв'язати по email дала б UNIQUE constraint на StudentId. Правильне рішення: оновити UserId на існуючому UserLink.

### Чому GithubToken шифрується через DataProtection
Токен дає доступ до private-репо студента — тримати у відкритому вигляді не можна.
`TokenProtector` шифрує через ASP.NET DataProtection; ключі персистяться у `dp-keys/`
(фіксована тека), щоб токени переживали рестарт.

### Чому клони репо чистяться фоново
`GradingService` кешує повні клони у `WorkRoot` за хешем URL і переиспользує їх, але
сам не видаляє → диск ріс би без меж (мертві/перейменовані репо, ~100 студентів).
`RepoCleanupService` щодня видаляє клони, що простоюють > `Grading:RepoRetentionDays`;
видалений клон просто переклонується наступного разу (жодного впливу на коректність).

## Відомі обмеження

1. Оцінює LLM (Gemini) — можливі нестабільність/помилки в межах prompt; пом'якшено
   строгими вимогами в `checks.json` і прозорою формулою score.
2. `TestsPassed/TestsTotal` завжди 0 — окремі xUnit-тести (lab-01 `tests/`) не підключені до пайплайну.
3. SQLite + `EnsureCreated` без міграцій: зміна схеми = видалити `autocheck.db` (є щоденний бекап).
4. Евристичний пошук файлу (без маппінгу коміт→завдання) може обрати не той файл — маппінг надійніший.

## Можливі покращення

1. Підключити реальний запуск тестів (build+xUnit) як додатковий сигнал поряд з Gemini.
2. Перехід SQLite → PostgreSQL + міграції EF Core для production-масштабу.
3. Кешування результатів Gemini для незмінного коду (економія квоти).
